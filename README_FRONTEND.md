# Frontend Plan: Tornscape Tabletop Simulator

Этот документ описывает архитектуру, текущее состояние и план реализации клиентской части (Frontend) веб-симулятора настольного варгейма **Tornscape**. Проект использует React, TypeScript и Zustand.

## 1. Текущее состояние и архитектура

**Стек:** React 19, TypeScript, Vite, Zustand (для стейт-менеджмента), SVG (для отрисовки поля).

**Структура проекта:**
*   `src/types/game.ts` — TypeScript-интерфейсы (`HexCoord`, `Unit`, `TerrainData`).
*   `src/lib/hex.ts` — Математика гексагональной сетки. Здесь лежат функции перевода координат в пиксели (`hexToPixel`), поиска соседей (`hexNeighbors`), генерации поля (`generateHexsonGrid`) и построения путей (`reachableHexes`).
*   `src/store/gameStore.ts` — Глобальное состояние (Zustand). Хранит юнитов, текущего игрока, лог боя, террейн. Точка входа партии — `startGameWithRosters()` (`src/store/gameStore.ts:172`), сброс — `resetGame()` (`src/store/gameStore.ts:193`), расстановка — `pickSpawnHexes()` (`src/store/gameStore.ts:44`).
*   `src/components/HexGrid.tsx` — Основной компонент визуализации поля.
*   `src/components/ArmyBuilder.tsx` — Экран сборки ростеров (каталог из БД, лимит очков), вызывает `startGameWithRosters()` и `onStart`.
*   `src/App.tsx` — Переключение экранов «сборка / игра», панель юнита, журнал боя, кубики.

**Ключевая концепция поля:**
Поле состоит из **гексонов** (макро-клеток). Каждый гексон — это фигура из **7 маленьких гексов** (1 центральный + 6 соседей вокруг него). В нашей реализации гексоны генерируются с использованием жестких смещений (`shiftQ`, `shiftR`), чтобы создать диагональные ряды (6 и 7 гексонов в ряду). Всё поле повернуто на `-40°` для удобства восприятия.

## 2. Проблема, которую нужно решить (Приоритет №1)

**Задача:** Визуально выделить границы каждого гексона (цветка из 7 гексов) яркой линией, при этом **внутренние перегородки** между 7 гексами одного гексона должны оставаться тонкими и темными.

**Что уже пробовали и почему не работает:**
1.  *Отрисовка большого шестиугольника поверх:* Не работает, так как гексон — это не идеальный шестиугольник с 6 углами, а фигура с **18 внешними гранями**. Большой шестиугольник пересекает маленькие гексы.
2.  *Вычисление соседей математически:* Из-за ручных сдвигов (`shiftQ`, `shiftR`) при генерации поля математические соседи не совпадают с реальным положением на экране. Контуры рисуются «мимо» гексов.

**Требуемый результат:**
На экране должно быть ровное поле. Внутри каждого гексона (7 гексов) линии тонкие. По внешнему периметру каждого гексона проходит толстая яркая линия (например, цвет `#88bbee`, толщина `3px`).

## 3. План реализации Frontend (Roadmap)

### Этап 1: Завершение визуализации поля (Выполнено)
*   [x] Написать корректный алгоритм отрисовки внешнего контура гексона.
    *   Реализовано в `getHexsonOutlinePaths()` (`src/lib/hex.ts`): собираются рёбра 7 гексов, внутренние (встречающиеся дважды) отбрасываются, внешние сшиваются в замкнутые ломаные. Результат — точный **18-угольник** без «швов».
    *   Вершины сопоставляются по целочисленным ключам решётки `(2q + r + du, 3r + dv)`, поэтому нет зависимости от погрешности float и от ручных сдвигов генерации.
*   [x] Убедиться, что при наложении слоев внутренние линии перекрываются, а внешние — остаются.
    *   Слои: заливка гексов с тонкой сеткой → границы гексонов (сначала все тёмные подложки, потом все светлые линии) → декор (укрытия, юниты).
*   [ ] Оптимизировать производительность SVG (возможно, использовать `clip-path` или маски).
    *   Контуры считаются один раз в `useMemo`, повторно от сетки не зависят.

#### Навигация по полю: зум и панорама (Выполнено)
*   [x] Размеры всех элементов заданы относительно `HEX_SIZE` (толщина сетки и границ, радиус юнита, шрифты укрытий, инициалов и HP) — масштабируются вместе с полем.
*   [x] Масштаб по умолчанию `INITIAL_ZOOM = 2` (`MIN_ZOOM = 0.7`, `MAX_ZOOM = 8`) — поле открывается крупно.
*   [x] Зум колесом мыши **относительно курсора**: нативный слушатель `wheel` с `{ passive: false }`, координаты курсора переводятся в систему viewBox через `getScreenCTM().inverse()`.
*   [x] Панорама перетаскиванием (pointer events). `setPointerCapture` вызывается только после порога 4px, поэтому обычный клик по гексу не «съедается»; после драга клик подавляется через `suppressClickRef`.
*   [x] Кнопки `+` / `−` / `⟲` (сброс) и подсказка по управлению поверх поля.
*   [x] Позиция камеры ограничивается `clampPan()` — нельзя уехать за пределы поля.

Зум и панорама реализованы не трансформацией SVG, а изменением `viewBox` (`zoomAbout()` + `clampPan()` в `src/components/HexGrid.tsx`): так толщина линий и размер шрифтов остаются постоянными в экранных пикселях, а визуально увеличивается само поле.

### Этап 2: Сборка Ростера (Army Builder)
*   [x] Каталог юнитов берётся из БД через REST API, а не из хардкода: `GET /api/factions` и `GET /api/units` (клиент — `src/lib/api.ts`, базовый URL через `VITE_API_URL`, по умолчанию `http://localhost:3001`).
*   [x] В модель `Unit` добавлены `points` (стоимость в очках) и `specialRules` (правила), миграция `add_unit_points`.
*   [x] Реализовать экран `ArmyBuilder.tsx` (появляется до старта игры).
*   [x] Логика: фильтр по фракции, поиск, лимит очков (`POINTS_LIMIT = 200`), блокировка добавления сверх лимита, счётчики и прогресс-бары по каждому игроку, удаление и очистка ростера.
*   [x] Состояние загрузки и ошибки с кнопкой «Повторить» (сообщение отличает «бэкенд не запущен» от ошибки API).
*   [x] После сборки `gameStore` инициализируется выбранным составом: `startGameWithRosters()` конвертирует шаблоны из БД в игровых юнитов, расставляет их на противоположных краях поля, сбрасывает ход и лог.
    *   Зона спавна считается от фактических пиксельных границ сгенерированного поля (первые/последние 25% по X), а не задаётся «магическими» координатами — юнит не может оказаться вне поля.
    *   Внутри зоны юниты выбираются от середины поля по вертикали с зазором 2 гекса (при нехватке — 1, затем 0), свободные гексы помечаются в общем `taken`, поэтому армии не пересекаются.
    *   Принадлежность юнита хранится явно в поле `Unit.player`, а не выводится из фракции: оба игрока могут собрать ростер из одной фракции.
    *   `App.tsx` переключает экраны (`isGameStarted`), а возврат в сборку вызывает `resetGame()` и сохраняет уже выбранные росторы.

### Этап 3: Игровая логика

## 4. Инструкция для ИИ / Разработчика

Контур гексона реализован в `getHexsonOutlinePaths()` (`src/lib/hex.ts`), отрисовка — в `src/components/HexGrid.tsx`.

**Как это работает:**
1.  Для центра гексона берутся он сам и 6 соседей, отфильтрованные по фактическому наличию в сетке (важно для краёв поля).
2.  У каждого гекса строятся 6 вершин через `hexCorners()` (единый источник геометрии вместе с `hexPath()`).
3.  Рёбра индексируются по ключам вершин: внутреннее ребро встречается дважды и отбрасывается, внешнее — остаётся.
4.  Оставшиеся рёбра сшиваются в замкнутые контуры по общим вершинам и сериализуются в SVG-path.

**Важно:** контур строится по целочисленным ключам вершин, а не по пиксельным координатам с округлением. Попытки «угадать» наружные вершины по углам (`60*i`, `60*i ± 30`) или нарисовать поверх большой шестиугольник дают неверный результат: у гексона 18 внешних граней, а не 6.
